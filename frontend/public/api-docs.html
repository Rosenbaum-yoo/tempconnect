TempConnect API v2.0

Die TempConnect Integration API ermöglicht programmatischen Zugriff auf die zentrale B2B-Plattform für temporäre Arbeitskräftevermittlung. Sie verbindet Kundenunternehmen (Companies) mit Personaldienstleistern (Agencies) über einen zweiseitigen Marketplace mit SLA-Garantien, Kapazitätsmanagement und vollständigem Deal-Workflow.

Base-URL: https://<ihre-instanz>/api

Datenformat: Alle Requests und Responses verwenden application/json.

Zeichensatz: UTF-8

Hinweis: Die API verwendet aktuell session-basierte Authentifizierung (Cookie). Eine token-basierte API-Key-Authentifizierung für Server-zu-Server-Integrationen ist auf der Roadmap.

Authentifizierung

TempConnect nutzt session-basierte Authentifizierung mit HTTP-Only-Cookies und CSRF-Schutz.

Auth-Flow

  1. CSRF-Token holen: GET /api/csrf → Session-Cookie wird automatisch gesetzt
  2. Login: POST /api/auth/login mit CSRF-Token im Header
  3. Authentifizierte Requests: Cookie tc.sid wird automatisch mitgesendet
  4. Mutierende Requests: Header x-csrf-token mit gültigem Token erforderlich

CSRF-Token abrufen

GET /api/csrf Kein Auth

Gibt ein CSRF-Token zurück und initialisiert die Session.

Response:

{
  "token": "a3f8c1e9b2d74..."
}
Dieses Token muss als x-csrf-token Header bei allen POST/PATCH/PUT/DELETE Requests mitgesendet werden.

Rollen & Organisationskontext

Benutzerrollen

RolleBeschreibungTypische Aktionen
companyKundenunternehmenNachfragen erstellen, Angebote annehmen, Personal anfordern
agencyPersonaldienstleisterKapazitäten anbieten, Angebote senden, Mitarbeiter verwalten
workerZeitarbeitnehmerEinsätze einsehen, Stundenzettel einreichen (Worker-Portal)

Organisationskontext

Jeder Benutzer gehört einer Organisation an. Der Org-Kontext wird serverseitig automatisch aufgelöst. Viele Endpunkte (Workers, Assignments, Organizations) arbeiten im Kontext der aktuellen Organisation.

Org-Rollen (RBAC)

Innerhalb einer Organisation existieren feingranulare Rollen:

owner · admin · program_manager · hiring_manager · supplier_manager · finance · member · recruiter · dispatcher · viewer

GET /api/my/requests/sent Gesendete Anfragen

Auth Alle eigenen gesendeten Anfragen.

Auth Alle an den Benutzer gerichteten Anfragen.

GET /api/requests/:id Anfrage-Details

Auth Gibt vollständige Details inkl. Compliance-Status, SLA-Events und Supplier-Scorecard zurück. Nur für Requester oder Receiver sichtbar.

PATCH /api/requests/:id/status Status ändern

Auth

Body: { "status": "ACCEPTED" }

Mögliche Status-Übergänge:

SENT → ACCEPTED / DECLINED (Receiver)

ACCEPTED → FINALIZED (Requester)

* → CANCELED (Requester oder Receiver)

Bei FINALIZED werden Kontaktdaten ausgetauscht und verwandte Anfragen als FILLED markiert.

OpenAPI Spezifikation

Die TempConnect API ist als OpenAPI 3.0.3 Spezifikation verfügbar. Die Spec-Datei kann für Client-Generierung, automatisierte Tests und Import in Postman/Insomnia verwendet werden.

Spec-Datei: /api/openapi/spec.json — OpenAPI 3.0.3, JSON-Format

Die Spezifikation enthält:

  • Alle öffentlichen Endpunkte mit Request/Response-Schemas
  • Komponentenschemas: User, Organization, Requisition, CapacityPost, Timesheet, TimesheetEntry, MatchResult, ServiceStatus, Error
  • Security-Schemes: Session-Cookie (tc.sid) + CSRF-Token
  • Server-Konfiguration für lokale Entwicklung und Produktion

Integrationshinweise

Session-Management

Die API verwendet HTTP-Only-Cookies für die Authentifizierung. Bei server-seitigen Integrationen muss der HTTP-Client Cookies speichern und bei Folge-Requests mitsenden (z.B. credentials: "include" bei Fetch, oder ein Cookie-Jar bei cURL/Axios).

CSRF-Workflow für Integrationen

# 1. Session + CSRF-Token holen
curl -c cookies.txt https://api.example.com/api/csrf

# 2. Login
curl -b cookies.txt -c cookies.txt \
  -H "x-csrf-token: TOKEN_AUS_SCHRITT_1" \
  -H "Content-Type: application/json" \
  -d '{"email":"...", "password":"..."}' \
  https://api.example.com/api/auth/login

# 3. Authentifizierter Request
curl -b cookies.txt \
  https://api.example.com/api/me

Was aktuell unterstützt wird

  • Session-basierte Authentifizierung (Cookie)
  • JSON-basierte REST-Endpunkte
  • Org-scoped Daten (automatischer Kontext)
  • Vollständiges CRUD für Marketplace, Workers, Assignments
  • Echtzeit-Notifications (Polling)

Was nicht unterstützt wird (Roadmap)

  • API-Key / Bearer-Token-Authentifizierung — geplant
  • WebSocket-/SSE-basierte Echtzeit-Events — geplant
  • Webhooks für Event-Benachrichtigungen — geplant
  • Explizite API-Versionierung (v2, v3) — bei Bedarf
Hinweis für Partner: Die aktuelle API ist primär für browser-basierte Clients optimiert. Server-zu-Server-Integrationen funktionieren, erfordern aber Session-/Cookie-Management. Eine dedizierte API-Key-basierte Partner-API ist in Planung.
